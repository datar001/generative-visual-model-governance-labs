# 第5章 DCT水印：当前书内最小实践

本实践在第2章的一张红杯图上写入16位消息，读取含水印PNG及JPEG质量75副本，并对未嵌入原图执行相同解码器。重点是区分已写入消息的恢复和任意图像也会产生的解码串。

## 运行与产物

按[环境与输入准备](../../examples/minimal/README.md)设置`LAB_ROOT`，先生成第2章的`red_2026.png`，再运行[最小代码](../../examples/minimal/05_watermark.py)：

```bash
python examples/minimal/05_watermark.py
```

代码固定种子2026生成16位消息，在8×8亮度块的两个DCT系数差中循环嵌入，强度为16。结果写入`$LAB_ROOT/minimal_examples_20261024/05_watermark/`，包括`marked.png`、`marked_q75.jpg`和三条记录的`decoded.json`。本入口可在CPU运行，不计算PSNR，也没有多强度、缩放、噪声或裁剪对照。

## 当前结果怎样解释

| 条件 | 实际写入的消息 | 解码串 | 已嵌入消息的逐位恢复率 |
|---|---|---|---:|
| 含水印PNG | `1001000010111110` | `1001000010111110` | 1.000 |
| 含水印JPEG75 | `1001000010111110` | `1001000010111110` | 1.000 |
| 未嵌入原图 | 无 | `1111100001111111` | 不适用 |

[原始三条解码记录](../../evidence/all_practice_alignment_20261025/outputs/05_watermark/decoded.json)保留代码直接输出。未嵌入图的`source_bits`只是用于比较的测试消息，没有实际写入该图；其`bit_accuracy=0.625`表示解码串与测试串有10/16位偶然相同，不能称为恢复了62.5%的水印，也不是误报率。书内未嵌入行的写入消息和恢复率均记为不适用。

这张图在当前参数下经JPEG75仍完整恢复消息，说明重复嵌入与投票在本例有作用；单图、单消息不能提供跨图稳健性或统计误报保证。解码器总会输出16位，若要判断是否存在水印，还需预先定义检出规则，用独立图像和消息测试。可见质量需要看细纹、平坦区和边缘，不能引用未由本代码计算的PSNR。
